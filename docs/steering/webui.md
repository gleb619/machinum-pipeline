# @mt/webui
← [Architecture](../guiding/architecture.md)

Path: `packages/webui/`

Admin server (h3 handlers; Nitro file-routing for dev, plain h3 + `node:http` for `mt serve` / the Bun binary). Serves the Vue frontend, REST API for run management, and SSE event stream from `events.jsonl`. Uses SQLite as an indicator/metadata store (v1 — not the source of truth; `.mt/` files remain canonical).

## API Routes


## SSE Events (`events.ts`)

Tails `.mt/runs/<runId>/events.jsonl` using file watching. Sends each appended JSON line as an SSE `data:` message with an `id:` byte offset. A reconnecting client sends `Last-Event-ID`; the route starts reading at that byte offset, so events are not replayed or duplicated. `?projectId=` resolves the run under the T203 mirror root instead of the serve root.

## SQLite (`server/plugins/sqlite.ts`, `server/utils/sqlite.ts`)

- `sqlitePlugin` — initializes DB on server start, creates tables if missing
- `initSqlite()` / `getDb()` / `closeSqlite()` — singleton DB access
- v1: only stores run index for quick listing (canonical data is in `.mt/` files)

## Standalone runtime (`server/standalone.ts`)

`createBackendApp()` mounts the same route handlers as Nitro on a plain h3 router, with the optional bearer
middleware first; `startBackend({port,host,uiDir,ui,token,projectRoot})` resolves the token, enforces the bind guard, then
acquires a shared listener from `@mt/core`'s registry (`acquireListener`), mounts the h3 app as the
listener's `'*'` fallback, and returns `{url,port,close}`. The same listener is reused by `hs://`
sources on that `host:port`, so a pipeline ingest endpoint and the admin UI answer on one port.
Static UI: `uiDir` (vite `dist`) or the embedded map `globalThis.__MT_UI__` (URL path -> embedded file, generated by
`packages/mt/scripts/build-bin.ts`), with SPA fallback to `index.html`; `/api/*` misses return 404. Built with
`tsc -p tsconfig.build.json` -> `dist/standalone.js`, exported as `@mt/webui/standalone`. Route handlers stay the
single source: adding a route file means also registering it in `createBackendApp()`.

### Auth (T202)

`startBackend()` resolves one bearer token, highest priority first:

1. explicit `startBackend({ token })` (the CLI resolves `--token-ref` first);
2. `MT_SERVE_TOKEN` (plaintext or a secret ref);
3. `mt.json -> serve.tokenRef` (a ref only: `env:NAME`, `vlt:NAME`, `keepass:TITLE`, `embed:NAME`).

When a token is configured, every `/api/*` request except `GET /api/health` needs
`Authorization: Bearer <token>`; a miss returns `401` with `{ "error": "Unauthorized" }` and
`WWW-Authenticate: Bearer`. Static UI GETs stay open. `GET /api/health` is intentionally open but
returns the minimal shape (`{ "status": "ok" }`) until the caller authenticates; with a valid bearer
token (or when no token is configured) it returns
`{ status, version, capabilities: { chrome, docker, playwright, ollama }, syncVersion: 1 }`.
Capability probes are cached 60 s, use a 2 s timeout and never throw. Comparison hashes both sides
with SHA-256 and uses `timingSafeEqual`, so different token lengths take the same path and nothing
leaks. The token is never logged.

No token + loopback host = open (back-compat). No token + non-loopback `--host` = startup error from
`assertSafeServeBind()` with an `MT_SERVE_TOKEN` / `--token-ref` fix hint; it refuses before listening.
The loopback/bind guard is **copied** from the router into `server/utils/serve-auth.ts` — `webui` must
not import `@mt/router` for it. `resolveServeTokenRef()` is re-exported for the CLI.

Nitro dev uses `server/middleware/serve-auth.ts` for the same token check (no bind guard: Nitro owns
the listener). TLS terminates outside `mt`: use an SSH tunnel (`ssh -L 7777:127.0.0.1:7777 host`) or a
reverse proxy. The embedded router routes share the same `/api/*` guard whenever `MT_SERVE_TOKEN` is set.

Client token input is not wired into the Vue UI, TUI or Chrome extension yet (out of scope for T202):
auth-enabled deployments use `curl` / the CLI or a wrapper that adds the header.

### Cross-process ingest forwarding

`POST /api/ingest/register {path, runId, targetUrl}` mounts `path` on the serve listener and forwards
requests to `targetUrl` (loopback-only, `http:`). A spawned `hs://` source with `MT_INGEST_PARENT`
uses it instead of binding the declared port: it binds an ephemeral loopback port, registers, and
deregisters with `DELETE /api/ingest/register {path}` on teardown. The h3 app never becomes an open
proxy: non-loopback targets are rejected, and `/api/*` paths are reserved. Forwarding state lives in
`server/utils/ingest-forwarder.ts` and is cleared by `startBackend`'s `close()`.

### Project sync API (T203)

Mirror root: `<serveRoot>/.mt/remote/<projectId>/`, sandboxed with `resolveInsideRoot` plus a
symlink-component walk. `projectId` comes from the client (`mt.json -> remote.projectId` or the
computed `<slug>-<root-hash8>`); invalid ids, absolute paths and `..` are `400`.

- `GET /api/sync/manifest?projectId=&scope=sources|outputs&runId=` returns
  `[{ path, size, sha256, mtime }]`. `sources` lists the mirror; `outputs` adds
  `.mt/runs/<runId>/**` plus relative pipeline `.to(...)` targets.
- `GET /api/sync/files?projectId=&path=&scope=&runId=` streams one file (octet-stream,
  `X-Mt-Sync-Sha256`). `path` must be a safe relative POSIX path; protected paths are rejected.
- `PUT /api/sync/files?projectId=` accepts a stream of frames:
  `uint32be headerLength | JSON header | body`. Header = `{ path, op?: "write"|"delete", size, sha256? }`.
  Writes are atomic; checksums are verified; delete is used by `--prune`.
  Caps: per-file `remote.sync.maxFileBytes` (20 MB default), 64 MB per request, 500 MB per mirror.
- `.env*`, vault/KeePass/embed files, `.git/`, `node_modules/` and `.mt/` (except output-scope
  `.mt/runs/<id>/` reads) are rejected server-side, even if a client asks for them.

`createBackendApp`/`startBackend` accept `projectRoot` (defaults to `MT_PROJECT_ROOT` or cwd); tests and
embedded servers use it to isolate mirrors and SQLite state.

### Embedded router (T197)

`createBackendApp()` mounts `createRouterApp()` from `@mt/router` (T197), so `mt serve` answers the admin API/UI
**and** the router API on one port: `/api/chat/completions`, `/api/translate*`, `/api/pool`, `/api/models`,
`/api/dashboard`, `/api/logs`. Router is on by default; `--no-router` opts out. `/api/health` belongs to the webui
(the router's health+vault info lives at `/api/pool` when embedded). Router token and rate-limit middleware stay
scoped to the mounted router routes; the admin API never requires `MT_ROUTER_TOKEN`. Allowed import direction:
`webui → router` only — the router itself still imports no `@mt/*` (`layers.arch.test.ts` pins it).

SQLite driver (`utils/sqlite.ts`): `bun:sqlite` under Bun (built in, embedded in the binary), `better-sqlite3`
(native addon, optional dependency of `mt`) under Node. Both are used through a minimal `Database` interface
(`exec`/`prepare().run`/`close`).

## Runner Registry (`server/utils/runner-registry.ts`)

In-process registry mapping `runId → Runner` for runs started via the API. Methods: `registerRunner`, `getRunner`, `removeRunner`.

Used by `/api/runs/:id/pause` and `/api/runs/:id/resume` to reach the live Runner object.

`POST /api/runs/start` (`start.ts`) is the only writer: it registers the Runner right after `runner.start()` (which mints
the runId before its first await) and calls `removeRunner` when the run settles, done or failed. A run started some
other way — `mt run`, `mt resume`, another backend process — is never in this registry, so pause/resume answers 404;
that 404 means "not live in this process", not "run does not exist" (run metadata stays readable via `GET /api/runs/:id`).

## Project context

`start.ts` builds its `GlobalContext` with `@mt/core`'s `loadGlobalContext(projectRoot)` — the same loader `mt run`
and `mt resume` use. `mt.json` (project name, `defaults`, `settings`, top-level `uris` aliases) and
`secrets.envFile` therefore apply to admin-UI runs exactly as they do to CLI runs; the route must not hand-roll a
context.

With `projectId`, the root is the sandboxed sync mirror `<serveRoot>/.mt/remote/<projectId>/` and the
`pipeline` body field is resolved inside it; traversal or outside-root paths are `400`. One active run
is allowed per project id (`409` on a duplicate); the slot is released when the run settles. This is
the server half of T204: the CLI pushes with the sync API, starts by `projectId`, streams SSE with
`Last-Event-ID` reconnect, and pulls `/api/runs/:id/artifacts` (output scope + `.mt/runs/<id>/`).

## Frontend Integration

The Vue 3 components package (`@mt/components`, `vite build` -> `dist/`) is served by the standalone runtime (see above): from disk (`mt` npm package `dist/ui`) or embedded in the Bun binary. In dev, Vite proxy handles UI requests. The UI talks to the embedded router same-origin (cost/pool/logs panels); there is no separate router UI to link out to (T197).

## Important Constraints

- The backend reads `.mt/` files for canonical data — never writes them (only the Runner does)
- SQLite is a queryable index, not the source of truth
- `runner-registry` only holds Runners for the current process lifetime — cross-process runs need file-based coordination

## Running

```bash
pnpm dev --filter=@mt/webui     # Dev with hot reload (Nitro dev server)
pnpm build --filter=@mt/webui   # tsc -> dist/standalone.js (used by `mt serve`)
pnpm --filter=@mt/webui build:nitro   # optional Nitro production bundle (.output/)
```

Or via CLI: `mt serve` (in-process) / `mt serve --detach` (background process); both work from the single-file binary.
