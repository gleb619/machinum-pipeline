# @mt/backend
← [Architecture](../architecture.md)

Path: `packages/backend/`

Admin server (h3 handlers; Nitro file-routing for dev, plain h3 + `node:http` for `mt serve` / the Bun binary). Serves the Vue frontend, REST API for run management, and SSE event stream from `events.jsonl`. Uses SQLite as an indicator/metadata store (v1 — not the source of truth; `.mt/` files remain canonical).

## API Routes

```
packages/backend/server/routes/api/
├── health.ts                         # GET /api/health
├── pipelines.ts                      # GET /api/pipelines — list discovered pipelines
├── runs/
│   ├── index.ts                      # GET /api/runs — list all runs
│   ├── start.ts                      # POST /api/runs — start a new run, registerRunner(runId)
│   ├── [id].ts                       # GET /api/runs/:id — run metadata (state.json)
│   └── [id]/
│       ├── items.ts                  # GET /api/runs/:id/items — paginated envelope list
│       ├── events.ts                 # GET /api/runs/:id/events — SSE stream
│       ├── pause.ts                  # POST /api/runs/:id/pause — 404 unless the Runner is live here
│       └── resume.ts                 # POST /api/runs/:id/resume — same registry lookup
```

## SSE Events (`events.ts`)

Tails `.mt/runs/<runId>/events.jsonl` using file watching. Sends each appended JSON line as an SSE `data:` message. Client reconnection is handled via `Last-Event-ID` header.

## SQLite (`server/plugins/sqlite.ts`, `server/utils/sqlite.ts`)

- `sqlitePlugin` — initializes DB on server start, creates tables if missing
- `initSqlite()` / `getDb()` / `closeSqlite()` — singleton DB access
- v1: only stores run index for quick listing (canonical data is in `.mt/` files)

## Standalone runtime (`server/standalone.ts`)

`createBackendApp()` mounts the same route handlers as Nitro on a plain h3 router; `startBackend({port,host,uiDir,ui})`
listens via `node:http` (Bun implements it, so it runs in the single-file binary) and returns `{url,port,close}`.
Static UI: `uiDir` (vite `dist`) or the embedded map `globalThis.__MT_UI__` (URL path -> embedded file, generated by
`packages/mt/scripts/build-bin.ts`), with SPA fallback to `index.html`; `/api/*` misses return 404. Built with
`tsc -p tsconfig.build.json` -> `dist/standalone.js`, exported as `@mt/backend/standalone`. Route handlers stay the
single source: adding a route file means also registering it in `createBackendApp()`.

SQLite driver (`utils/sqlite.ts`): `bun:sqlite` under Bun (built in, embedded in the binary), `better-sqlite3`
(native addon, optional dependency of `mt`) under Node. Both are used through a minimal `Database` interface
(`exec`/`prepare().run`/`close`).

## Runner Registry (`server/utils/runner-registry.ts`)

In-process registry mapping `runId → Runner` for runs started via the API. Methods: `registerRunner`, `getRunner`, `removeRunner`.

Used by `/api/runs/:id/pause` and `/api/runs/:id/resume` to reach the live Runner object.

`POST /api/runs` (`start.ts`) is the only writer: it registers the Runner right after `runner.start()` (which mints
the runId before its first await) and calls `removeRunner` when the run settles, done or failed. A run started some
other way — `mt run`, `mt resume`, another backend process — is never in this registry, so pause/resume answers 404;
that 404 means "not live in this process", not "run does not exist" (run metadata stays readable via `GET /api/runs/:id`).

## Frontend Integration

The Vue 3 frontend (`@mt/frontend`, `vite build` -> `dist/`) is served by the standalone runtime (see above): from disk (`mt` npm package `dist/ui`) or embedded in the Bun binary. In dev, Vite proxy handles frontend requests.

## Important Constraints

- The backend reads `.mt/` files for canonical data — never writes them (only the Runner does)
- SQLite is a queryable index, not the source of truth
- `runner-registry` only holds Runners for the current process lifetime — cross-process runs need file-based coordination

## Running

```bash
pnpm dev --filter=@mt/backend     # Dev with hot reload (Nitro dev server)
pnpm build --filter=@mt/backend   # tsc -> dist/standalone.js (used by `mt serve`)
pnpm --filter=@mt/backend build:nitro   # optional Nitro production bundle (.output/)
```

Or via CLI: `mt serve` (in-process) / `mt serve --detach` (background process); both work from the single-file binary.
